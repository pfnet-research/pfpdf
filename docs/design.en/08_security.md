# 8. Security model

## 8.1 Trust model

Because pfpdf processes raw HTML and user scripts, it is a local build tool that trusts its input documents. It is not designed to serve as a CI service for content submitted by arbitrary users.

`SECURITY.md` communicates at least the following points to users:

- Do not run untrusted documents
- Raw HTML, scripts, and external URLs may be executed or fetched by Chromium
- GitHub.com-style post-render sanitization is not performed, and GFM's Disallowed Raw HTML tag filter is likewise not applied; flexibility takes priority
- Raw HTML and custom templates can read local files accessible to the pfpdf process and send them to remote endpoints. The renderer is not a sandbox for untrusted input
- `..`, absolute paths, and symlink targets of static local resources are not restricted by an allowlist limited to the input root
- Local paths generated by scripts at run time fall outside the static resource graph, and the renderer does not guarantee their resolution
- Direct references to host fonts are a means of avoiding redistribution; they do not grant usage rights or the right to embed fonts into PDFs
- Custom templates and logos are treated as trusted input whose rights and contents the user has verified
- Which private channel to use for reporting vulnerabilities
- Which release series are supported

## 8.2 Implementation principles

- Never use `shell: true` for child processes. Never assemble shell strings; launch with argument arrays
- Send no telemetry, update checks, or crash reports externally
- The browser is either managed by the pinned Vivliostyle CLI's standard mechanism or a path explicitly specified by the user
- The loopback `AssetServer` binds only to `127.0.0.1`. The resource manifest is used for renderer-neutral URL resolution and is not treated as a security boundary for file access
- When a font file's embedding restrictions can be detected, do not ignore them; display the font name and how to address the problem
- Do not use predictable fixed names for temporary paths
- Create the workspace with permissions readable only by the user, and create the sibling temporary file for the final output with exclusive create. Never reuse an existing symlink or file as temporary output
- Do not disable the Chromium sandbox without reason
- Separate the browser binary cache from the execution profile, and never use the user's existing browser profile or cookie store
- Browser download, integrity checking, and cache extraction are the responsibility of the Vivliostyle CLI and the browser manager, and are not reimplemented in pfpdf
- Child processes inherit the caller's environment variables like any ordinary CLI tool. Input documents and custom templates are treated as trusted code that may reference them
- Diagnostics display and save the renderer's output unmodified. Users who do not want input-derived control characters or credential-bearing URLs in the logs should adjust the document and the execution environment
- YAML front matter is read as a mapping with an existing YAML library's JSON schema, and only the names and types of the metadata fields pfpdf uses are checked
- HTML, CSS, URLs, and OpenType are processed on the token or table boundaries of dedicated parsers, avoiding regular-expression re-parsing and unvalidated offset reads
- A finite deadline applies to the entire renderer phase, and after timeout the children and listeners are reclaimed. Even with trusted input, never wait indefinitely on a stalled browser download, script, or browser

## 8.3 Position on sandboxing

- pfpdf's local resource graph is a mechanism for correctness; it is not a security boundary against untrusted input
- Trusted scripts inside the document can read same-origin resources and send them to remote endpoints, so the AssetServer does not guarantee confidentiality
- The Chromium sandbox is maintained as defense in depth, but is not used to represent the processing of untrusted documents as safe
- Fetch results of remote resources are not guaranteed, and the README and `SECURITY.md` state explicitly that reproducibility, network errors, and the possibility of credential leakage are the user's responsibility

## 8.4 Ubuntu's user namespace restrictions

Ubuntu 23.10 and later restrict unprivileged user namespaces, so Chromium's sandbox may fail to start even when every required shared library is present. pfpdf distinguishes sandbox failures from missing-library errors. The tutorial's troubleshooting chapter documents workarounds that require root access, such as adding an AppArmor profile; pfpdf never changes privileged settings automatically.
