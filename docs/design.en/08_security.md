# 8. Security model

## 8.1 Trust assumptions

pfpdf is a local build tool that can process raw HTML and user scripts. It therefore assumes that input documents are trusted. Use as a CI service that processes input from arbitrary users is not supported.

`SECURITY.md` must include at least the following information for users:

- Do not run untrusted documents
- Chromium may process raw HTML, execute scripts, and fetch resources from external URLs
- GitHub.com-style sanitization after conversion to HTML is not performed, and GFM's Disallowed Raw HTML tag filter is likewise not applied; flexibility takes priority
- Raw HTML and custom templates can read local files accessible to the pfpdf process and send them to remote endpoints. The renderer is not a sandbox for untrusted input
- References to static local resources using `..`, absolute paths, or symlinks are not restricted by an allowlist limited to the input root
- Local paths generated by scripts at run time fall outside the static resource graph, and the renderer does not guarantee their resolution
- Direct references to host fonts are a means of avoiding redistribution; they do not grant usage rights or the right to embed fonts into PDFs
- Custom templates and logos are treated as trusted input whose rights and contents the user has verified
- Which private channel to use for reporting vulnerabilities
- Which release series are supported

## 8.2 Implementation principles

- Never use `shell: true` for child processes. Never assemble shell strings; launch with argument arrays
- Send no telemetry or crash reports externally, and make no external requests to check for updates
- Use either a browser managed by the pinned Vivliostyle CLI's standard mechanism or one whose path the user explicitly specifies
- The loopback `AssetServer` binds only to `127.0.0.1`. The resource manifest is used for URL resolution independent of the renderer and is not treated as a security boundary for file access
- When embedding restrictions are detected in a font file, do not ignore them; display the font name and how to address the problem
- Do not use predictable fixed names for temporary paths
- Create the build workspace with permissions that allow only the user to read it. Use exclusive creation for the temporary file placed in the same directory as the final output. Never reuse an existing symlink or file as temporary output
- Do not disable the Chromium sandbox without reason
- Separate the browser binary cache from the runtime profile, and never use the user's existing browser profile or cookie store
- Browser download, integrity checking, and cache extraction are the responsibility of the Vivliostyle CLI and the browser manager, and are not reimplemented in pfpdf
- Child processes inherit the caller's environment variables like any ordinary CLI tool. Input documents and custom templates are treated as trusted code that may reference them
- Display and save renderer diagnostics without modification. Users who do not want input-derived control characters or credential-bearing URLs in the logs should adjust the document and the execution environment
- YAML front matter is read as a mapping with an existing YAML library's JSON schema, and only the names and types of the metadata fields pfpdf uses are checked
- Process HTML, CSS, URLs, and OpenType at token or table boundaries using dedicated parsers. Avoid parsing them again with regular expressions or reading from unvalidated offsets
- Apply a deadline to the entire renderer phase. After a timeout, terminate and clean up child processes and stop the server from listening. Even with trusted input, never wait indefinitely on a stalled browser download, script, or browser

## 8.3 Position on sandboxing

- pfpdf's local resource graph is a mechanism for resolving resource references correctly; it is not a security boundary against untrusted input
- Trusted scripts inside the document can read same-origin resources and send them to remote endpoints, so the `AssetServer` does not guarantee confidentiality
- The Chromium sandbox is maintained as defense in depth, but is not used to represent the processing of untrusted documents as safe
- Fetch results of remote resources are not guaranteed. The README and `SECURITY.md` must state explicitly that ensuring reproducibility and addressing network errors and the risk of credential leakage are the user's responsibility

## 8.4 User namespace restrictions on Ubuntu

Ubuntu 23.10 and later restrict unprivileged use of user namespaces. As a result, Chromium's sandbox may fail to start even when every required shared library is present. pfpdf distinguishes sandbox failures from missing-library errors in its diagnostics.

The tutorial's troubleshooting chapter must document workarounds that require root access, such as adding an AppArmor profile. pfpdf never changes privileged settings automatically.
