# 1. 対象範囲と基本方針

## 1.1 pfpdf とは

pfpdf は、Markdown 文書を HTML 経由で PDF へ変換するコマンドラインツールです。Node.js と npm を導入済みの利用者が、リポジトリーをクローンせずに次の 1 コマンドで PDF を生成できることを第一の目標とします。

```bash
npx @pfnet-research/pfpdf@latest --input foo --output foo.pdf
```

CI や長期保存する手順書では `latest` を使わずバージョンを固定します。

```bash
npx --yes @pfnet-research/pfpdf@0.1.0 --input foo --output foo.pdf
```

## 1.2 `v0.1.0` の目標

- Node.js と同梱の依存関係だけで動作する
- `npx @pfnet-research/pfpdf` を利用者向け CLI の唯一の正式な導入経路とする
- 外部の Python 環境を要求しない
- CommonMark を包含する正式な GitHub Flavored Markdown（GFM）の構文を原則すべて扱う
- `これは**「重要」**です` のような、全角約物・括弧を含む日本語の強い強調（strong emphasis）を空白なしでも確実に `<strong>` へ変換する
- インラインとブロックの生の HTML を扱い、Markdown だけでは表現できないレイアウトの自由度を維持する
- 表紙、目次、改ページ、数式、コードハイライト、ローカル画像を扱える
- 再配布可能な標準フォントを既定とし、ホストフォントは明示的に許可された場合だけ読み込む
- 複数の同梱テンプレート（`academic` / `book` / `compact` / `default` / `notebook` / `pfn` / `technical`）を選択でき、ロゴなど同梱しないアセットは利用側から指定できる
- 文書設定はフロントマターで管理して CLI 引数で上書きでき、実行設定は CLI 引数で制御できる
- 入力元ディレクトリーを変更せず、一時ファイルを正常終了時と捕捉可能な異常終了時に回収する
- 異常時は部分的な成果物を成功扱いせず、非 0 の終了コードを返す
- Markdown ファイルの境界が GFM ブロックの意味を変えないよう各ファイルを独立して解析し、静的なローカルリソースはレンダラーに依存しないマニフェストで解決する
- レンダラーの準備、文書の準備が整うまでの待機（readiness）、描画に期限を設ける。ブラウザーのダウンロードや、スクリプト・ブラウザーの動作が止まった場合も無期限に待たない
- macOS aarch64 と Linux x86_64 を主要サポート、Windows x86_64 と Linux aarch64 を追加サポートとし、4 環境すべてを CI で検証する

## 1.3 `v0.1.0` の非目標

- 全 OS でバイト単位に同一な PDF の生成
- 信頼できない Markdown や生の HTML を安全に実行するサンドボックスの提供
- PyPI、Homebrew、単体バイナリへの同時公開
- GUI プレビューや常駐型のファイル監視モード
- PDF/X、CMYK、入稿向けプリフライト検査の品質保証
- GitHub リポジトリーの文脈を必要とするメンション、Issue / Pull Request への参照など、GitHub.com 固有の後処理の完全再現
- GitHub.com と同じ HTML のサニタイズ。pfpdf は信頼できる文書を対象とし、生の HTML を保持する
- 単一ファイルとして配布可能な HTML の生成。生成 HTML は PDF レンダラーへの入力とテストにだけ使用する
- `SIGKILL`、電源断、OS のクラッシュ時における作業ディレクトリーやブラウザープロセスの確実な回収
- 同一出力先を対象とする複数プロセス間の調停と、`SIGKILL` / 電源断後に出力ファイルと同じディレクトリーに残った一時ファイルに対する自動復旧処理
- スクリプトが実行時に生成する任意のローカルパス、DOM、ネットワーク応答を事前に発見してレンダラーへ公開すること
- リモートリソースの完全性、応答時間、内容のスナップショット、失敗の分類を保証すること
- Nix Flake、Nix パッケージ、Nix 固有の再現環境の提供

## 1.4 npx での利用を優先する

一般利用者向けの配布経路は npm パッケージとします。`package.json` の `bin` に `pfpdf` を登録し、グローバルインストールを要求せず `npx` または `npm exec` から起動できるようにします。

- 対応する Node.js のバージョンは、固定したバージョンの Vivliostyle CLI の要件に合わせて決定し、`package.json` の `engines`、起動時検査、CI で同じ条件を使う
- npm の `engines` は `npx` 実行では強制されないため、CLI のエントリーポイントは古い Node.js でも構文エラーにならない形式へビルドする。起動直後に Node.js のバージョンを検査し、非対応なら明確な診断を出して終了コード `1` で失敗する
- npm パッケージに CLI、変換処理、テンプレート、CSS、MathJax、highlight.js、標準フォントを含める
- ブラウザーの取得とキャッシュ管理は、固定したバージョンの Vivliostyle CLI と、その依存関係にある Puppeteer 系ブラウザーマネージャーの標準動作に任せる。pfpdf は独自のダウンローダー、キャッシュのロック、不完全なダウンロードからの復旧、不要なキャッシュの削除を実装しない
- 初回にはブラウザーのダウンロードで大量のデータを取得する場合があることを README で明示する
- `--browser-path` で既存の互換ブラウザーを明示できるようにする
- Linux ではブラウザーのアーカイブだけでは共有ライブラリーが揃わないため、対応ディストリビューションと必要なパッケージを 07 章とチュートリアルのトラブルシューティング章に列挙する。`--doctor` で不足するライブラリーを可能な範囲で報告し、root 権限で暗黙にインストールしない

### 対応環境

| OS / アーキテクチャー | サポート水準 | 備考 |
|---|---|---|
| macOS aarch64 | 主要サポート | Apple Silicon。Node.js のテストと実際のブラウザーによる PDF 生成を CI で検証する |

## 1.5 CLI の配布経路は npm に限定する

`v0.1.0` の利用者向け CLI の正式な導入経路は npm / npx だけとします。ソースコードからの利用と CI では `package-lock.json`、公開 CLI では配布アーカイブ内の `npm-shrinkwrap.json` で依存関係ツリーを固定します。検証済みの Node.js バージョン範囲と合わせて再現性を確保します。

## 1.6 組み込み機能はブラウザー取得後にオフラインで使えるようにする

数式とコードハイライトに必要なファイルは CDN から取得せず、固定バージョンをパッケージに含めます。

- npx 版は npm パッケージとブラウザーの初回取得にネットワークを使う
- npm パッケージとブラウザーがキャッシュ済みなら、pfpdf の組み込み機能だけを使う標準文書はネットワークなしで PDF 化できる
- 利用者自身が記述したリモート画像、スタイルシート、スクリプトについては利用者の責任でネットワークへアクセスする
- 同梱の MathJax による組版と highlight.js によるコードハイライトはビルド時の変換処理として HTML を組み立てる前に完了させる。変換済みの HTML だけを Vivliostyle がページに分割することを結合テストで確認する
- 同梱の MathJax / highlight.js の初期化・変換に失敗した場合と、利用者が文書の準備完了を通知する仕組み（document readiness contract）に登録した Promise が拒否された場合は、成功扱いしない。pfpdf は、利用者が指定したリモートリソースのタイムアウトや DNS / TLS / HTTP エラーを分類せず、その扱いや出力の安定性を保証しない。これらは利用者の責任とする
- ブラウザーの確認と取得、文書の準備が整うまでの待機、PDF の描画・後処理・構造検査には既定 300 秒の共通の期限を適用し、必要な文書だけ明示的に上書きできるようにする。タイムアウトを無期限にする値は提供しない

## 1.7 設定はフロントマターと CLI 引数に限定する

プロジェクト設定ファイルは設けません。文書の内容と見た目を決める設定はフロントマターへ記録し、リポジトリーごとの実行設定は Makefile、npm スクリプト、CI ワークフローなどに CLI 引数として記録します。

設定の優先順位は次のとおりです。

```text
明示的な CLI 引数 > フロントマター > 組み込み既定値
```

`template` / `toc` / `cover` / `logo` はフロントマターに記録し、対応する CLI オプションを指定した場合は、その実行だけ上書きします。ブラウザーのパス、追加フォントのディレクトリー、ホストフォントの使用、タイムアウト、作業ディレクトリーの保持、ログレベルは CLI だけで指定します。

再現可能ビルドで標準的に使われる環境変数 `SOURCE_DATE_EPOCH` と、子プロセスが通常継承する一般的な環境変数は、この設定優先順位とは別に扱います。

## 1.8 正本と翻訳の規則

リポジトリー内の長期的な仕様・設計・利用方法は、次の 4 つのディレクトリーへ集約します。

| ディレクトリー | 役割 | 言語上の位置付け |
|---|---|---|
| `docs/design.ja/` | 実装方針、アーキテクチャー、互換性、セキュリティー、設計判断 | 日本語の正本 |
| `docs/tutorial.ja/` | 導入から GFM、生の HTML、数式、テンプレート、CLI までの利用例 | 日本語の正本 |
| `docs/design.en/` | 設計書の英訳 | 日本語版に従う翻訳 |
| `docs/tutorial.en/` | チュートリアルの英訳 | 日本語版に従う翻訳 |

- 日本語版と英語版は同じ番号・ファイル名・章構成を使い、対応関係を機械的に確認できるようにする
- 仕様解釈が日英で衝突した場合は日本語版を正とし、英語版を修正する
- 日本語版を変更するプルリクエストでは対応する英語ファイルも同じプルリクエストで更新する
- README は導入用の短い入口と各正本・英訳への案内に留め、詳細仕様を重複させない
- リポジトリー内のすべての `AGENTS.md` は、正本を日本語で書く原則の例外として英語で記述する。エージェント向け規約の設計上の根拠は設計書へ置き、`AGENTS.md` には作業規則と正本への参照だけを簡潔に記載する
