# 9. 設計判断の記録

この章では、複数の妥当な選択肢があった事項について、採用案・非採用案とそれぞれの理由、利点と欠点、再検討条件を記録します。判断を置き換えた場合も過去の却下理由を消さず、置換済みであることを状態欄に記し、新しい判断へつなぎます。設計理由はコミットや Issue だけに記録せず、この章に残します。

各判断は次の形式で記録します。

- 状態と決定日
- 解決する問題、制約、評価基準
- 検討した選択肢
- 採用案と採用理由
- 採用しなかった案と、それぞれを採用しなかった具体的な理由
- 採用案の欠点、運用上の結果、既知のリスク
- 実装・テストでの検証方法
- 将来再検討する条件

## DD-01: Markdown パーサーに既存の GFM ライブラリーを採用する

- 状態: 採用 (2026-08)
- 問題: Markdown 変換の実装方法。独自パーサーは仕様を網羅する実装にも、その保守にも費用がかかる
- 選択肢: (a) 独自パーサーを実装する、(b) 保守されている GFM 対応ライブラリーのバージョンを固定して利用する
- 採用: (b)。GFM 仕様の適合例で検証でき、pfpdf 固有の機能（目次、数式、改ページ、日本語の強い強調）を明示的な拡張として分離できる
- 非採用理由: (a) は GFM の全構文を自前で網羅する必要があり、仕様追従の負担が大きい。部分実装では、利用者が「書けるはずの記法が変換されない」問題に直面する
- リスク: パーサーライブラリーの保守停止。バージョン固定と適合テスト群により、乗り換え時の挙動差を検出できるようにする
- 検証: `GfmAdapter` に対する、固定版 GFM 仕様の適合テスト群
- 再検討条件: 採用ライブラリーの保守停止、または仕様に適合できない不具合が長期間修正されない場合

## DD-02: 日本語の強い強調は区切り文字を処理する層の拡張で対応する

- 状態: 採用 (2026-08)
- 問題: CommonMark の flanking rule（区切り文字の前後関係を判定する規則）では、`これは**「重要」**です` のような全角約物を含む強い強調（strong）が認識されない
- 選択肢: (a) 構文解析後の正規表現 / HTML 置換で補正する、(b) パーサーの区切り文字を処理する層で CJK-friendly 拡張を使う、(c) 仕様どおりとして対応しない
- 採用: (b)。コードスパン、生の HTML、リンク先を壊さずに、トークン単位で正しく判定できる
- 非採用理由: (a) はコードブロックや生の HTML 内の `**` を誤変換する危険が高く、文脈を再解析することになる。(c) は日本語文書で頻出する自然な記法を書けないままにする
- リスク: 拡張の保守状況に依存する。標準機能または既存拡張で満たせない場合だけ、同等の区切り文字規則を最小限実装する
- 検証: 変換対象・非対象を網羅するフィクスチャー（第7章）
- 再検討条件: CommonMark 本体が CJK の flanking rule を改善した場合

## DD-03: 生の HTML はタグフィルターを適用せず、そのまま通す

- 状態: 採用 (2026-08)
- 問題: GFM の「Disallowed Raw HTML」タグフィルターを適用するか
- 選択肢: (a) GitHub.com と同様にフィルターを適用する、(b) 信頼済みの入力として保持する
- 採用: (b)。pfpdf は信頼済みローカル文書向けのビルドツールであり、`style` / `script` を含む生の HTML はレイアウトの自由度に必要
- 非採用理由: (a) はサンドボックスなしでは信頼できない入力を安全にしきれない一方、正当な表現手段を奪う
- リスク: 信頼できない文書を処理すると任意のスクリプトが実行される。入力を信頼する方針を README と `SECURITY.md` に明記する（第8章）
- 検証: 生の HTML を保持するフィクスチャーを用意し、適合テスト群では意図的な差異として記録する
- 再検討条件: 信頼できない入力の処理を正式サポートする場合（その際はサンドボックス設計が前提）

## DD-04: ループバックの `AssetServer` をセキュリティー境界としない

- 状態: DD-11 で置換済み (2026-08)
- 問題: Vivliostyle CLI が URL 入力を必要とする場合のローカルリソース配信方法
- 選択肢: (a) 厳密なファイル対応表、ビルドトークン、オリジンの許可リストを持つサーバー、(b) 信頼済みの入力を前提とする単純な静的ファイルサーバー
- 当初採用: (b)。入力を信頼する方針のもとでは、(a) の機構は防御効果に対して複雑さと故障点が大きいと判断した
- 非採用理由: (a) は生の HTML が任意のローカルファイルを参照できるという前提と矛盾し、安全性の錯覚を与える
- リスク: `AssetServer` が多用途に流用される可能性。設計文書と `SECURITY.md` でセキュリティー境界ではないことを明示する
- 検証: 静的配信、CORS、ポートのクローズを確かめる結合テスト
- 置換理由: `..` / 絶対パス / 入れ子の CSS を正しく解決するには、静的リソースの対応表が必要だった。また、ワイルドカード CORS を使う単純なサーバーは、別のローカル Web ページから偶発的に読み取れるファイルの範囲を不必要に広げる。サンドボックスを提供しなくても、厳密なファイル対応表とランダムトークンには、正しさの確保と多層防御の価値がある

## DD-05: ブラウザー管理は Vivliostyle CLI へ委譲する

- 状態: 採用 (2026-08)
- 問題: PDF 描画に使う Chromium の取得・キャッシュ管理
- 選択肢: (a) pfpdf が独自にブラウザーをダウンロード・管理する、(b) 固定版 Vivliostyle CLI と Puppeteer 系ブラウザー管理機構の標準的な仕組みに任せる
- 採用: (b)。ダウンロードの完全性、キャッシュの構成、プラットフォームごとの差は上流が既に解決しており、重複実装は保守負担と不整合の原因になる
- 非採用理由: (a) はキャッシュのロック、途中で失敗したダウンロードの復旧、不要なキャッシュの削除まで自前で担い、上流の変更に追従し続ける必要がある
- リスク: 上流のブラウザー管理方針の変更に影響を受ける。代替手段として `--browser-path` による明示的な上書きを提供する
- 検証: ブラウザーがない状態での初回実行と、ブラウザーパスの明示指定を確かめる結合テスト
- 再検討条件: 上流のブラウザー管理が pfpdf の要件を満たさなくなった場合

## DD-06: レンダラーは単一の描画経路にする

- 状態: 採用 (2026-08)
- 問題: 複数のレンダラーバックエンドと利用者向けの選択設定は、実行経路、診断、後処理、テストの組合せを増やし、同じ入力に対する挙動差を生み得る
- 選択肢: (a) 複数のバックエンドと明示的な切替を維持する、(b) 単一の Vivliostyle 描画経路に限定する
- 採用: (b)。`AssetServer` と Vivliostyle CLI の子プロセスに描画経路を限定し、設定・診断・失敗分類を一意にする
- 非採用理由: (a) は利用されないバックエンドにも配布、互換性、タイムアウト、後処理の保守を要求し、品質保証を分散させる
- リスク: 特定環境でブラウザーを起動できない場合に、別のバックエンドへ切り替えられない。`--doctor`、ブラウザーパスの明示指定、対応環境の検証で診断と移行を支援する
- 検証: 公開 CLI にレンダラー選択がなく、結合テストが実際の単一経路を通ることを確認する
- 再検討条件: 別の描画エンジンが独立した利用価値と保守可能な互換性の契約を持つ場合

## DD-07: 設定はフロントマターと CLI 引数に限定し、CLI を常に優先する

- 状態: 採用 (2026-08)
- 問題: 設定元の種類と優先順位
- 選択肢: (a) プロジェクト設定ファイルを導入する、(b) pfpdf 固有の環境変数を使う、(c) 文書設定をフロントマター、実行設定を CLI へ置く
- 採用: (c)。設定ファイルには探索順序・マージ規則・相対パスの基準という新たな仕様が必要になる。環境変数はバージョン管理されず、「どの設定が効いたか」の診断を難しくする。文書設定は既定値、フロントマター、CLI の順に上書きする。繰り返し使う実行設定は、Makefile や CI ワークフローに CLI 引数として記録する。再現可能ビルドの標準的な入力である `SOURCE_DATE_EPOCH` と、一般的なプロセスの環境変数はこの制限の対象外とする
- 非採用理由: (a) は別形式のプロジェクト設定を増やす。(b) は文書の意図を Markdown から分離し、設定をリセットする CLI オプションと設定元の組合せを増やす
- リスク: 実行設定では長い引数列が必要になる場合がある。ラッパースクリプトで緩和する
- 検証: 既定値 / フロントマター / CLI の優先順位、CLI 専用設定、有効な設定値と設定元を確かめる単体テスト
- 再検討条件: 実行設定項目が大幅に増え、CLI で管理困難になった場合

## DD-08: 生成 HTML を公開出力形式にしない

- 状態: 採用 (2026-08)
- 問題: HTML を PDF と並ぶ出力形式として公開するか
- 選択肢: (a) 単一ファイルの HTML 出力を提供する、(b) HTML はレンダラーへの入力とテスト専用にする
- 採用: (b)。単一ファイル化にはアセットの再帰的な埋込み、データ URL 化、フォントのサブセット化が必要で、PDF 生成という主目的に対して複雑さが大きい
- 非採用理由: (a) はリソースグラフの完全な追跡を要求し、生の HTML 内の動的参照と原理的に両立しない
- リスク: HTML 出力を求める利用者の要望に応えられない。内部形式の HTML は、レンダラーへ渡す `document.html` と同一のビルダー出力をテストで検査する
- 検証: ビルダー出力と Vivliostyle 入力の同一性を検査する結合テスト
- 再検討条件: `v0.2.0` 以降で単一ファイル HTML の需要と実装コストを再評価する場合

## DD-09: 日本語文書を正本、英語文書を翻訳とする

- 状態: 採用 (2026-08)
- 問題: 設計文書とチュートリアルの多言語管理
- 選択肢: (a) 英語のみ、(b) 英語正本 + 日本語訳、(c) 日本語正本 + 英語訳
- 採用: (c)。主要な読者・執筆者が日本語話者であり、日本語組版（全角約物を含む強い強調、日本語フォント）が pfpdf の中核機能であるため、正確さを保ちやすい言語を基準とする
- 非採用理由: (a) は主要利用者にとっての読みやすさを損なう。(b) は日本語固有の仕様（約物、日付書式）を英語で先に規定する不自然さがある
- リスク: 英語話者の貢献者には翻訳が二次情報になる。ファイルの対応検査と同一プルリクエストでの同時更新を CI で必須とし、乖離を防ぐ
- 検証: `check-doc-translations.mjs` と文書ビルドの CI
- 再検討条件: 貢献者の言語構成が大きく変わった場合

## DD-10: エラー時は直ちに停止し、部分出力を成功にしない

- 状態: 採用 (2026-08)
- 問題: 複数の Markdown の一部が変換エラーになった場合の挙動
- 選択肢: (a) エラーのファイルを読み飛ばして続行する、(b) 文書全体を失敗させ、0 以外の終了コードを返す
- 採用: (b)。読み飛ばしは内容が欠落した PDF が成功として配布される事故を生み、CI でも検出できない
- 非採用理由: (a) は一見親切だが、終了コード `0` のまま内容が欠ける方が実害が大きい
- リスク: 大きな文書で 1 か所の誤りが全体を止める。エラー位置を明確に診断して緩和する
- 検証: 全エラー経路が 0 以外の終了コードを返すことを確かめる単体・結合テスト
- 再検討条件: なし

## DD-11: 静的リソースグラフと、トークン付きの厳密なファイルサーバーを使う

- 状態: DD-18 で置換済み (2026-08)
- 問題: Markdown、生の HTML、入れ子の CSS から参照されるローカルアセットを正しい基準パスで解決しつつ、レンダラーへ同じ `document.html` を渡す必要がある
- 選択肢: (a) 入力ディレクトリー全体やファイルシステムのルートを配信する、(b) アセットをすべてデータ URL として HTML に埋め込む、(c) 静的参照をパーサー上でグラフ化し、論理 URL へ書き換える
- 採用: (c)。レンダラー固有のパスを HTML から除去でき、配信を必要なリソースに限定でき、CSS の循環したインポートも明示的に扱える。サーバーはランダムなパストークンと厳密なファイル対応表を使い、ブラウザーと同じホストのループバックインターフェースで起動する
- 非採用理由: (a) は絶対パスを扱うために配信範囲が過度に広くなり、パスの衝突とプラットフォーム差も残る。(b) は大きなフォント / 画像のメモリー使用を増やし、単一 HTML 出力を目標としない方針にも反する
- リスク: HTML / CSS から静的 URL を抽出する処理が新たに複雑さを増す。スクリプトが動的に生成するローカルパスは対象にできず、レンダラーでの解決を保証しない。ビルド中のアセット内容のスナップショットも作らない。専用パーサー、訪問済み集合、マニフェストのフィクスチャーで緩和する
- 検証: 入れ子の `@import`、`url()`、`srcset`、絶対パス / `..` / シンボリックリンク、循環、論理 URL、トークン / パストラバーサル / バイト範囲の結合テスト。同じ HTML のバイト列をサーバーから配信することも検査する
- 再検討条件: 上流レンダラーが特定のレンダラーに依存しないリソースプロトコルを提供し、独自グラフを安全に削除できる場合

## DD-12: 複数の Markdown はファイルごとに独立して構文解析し、AST を結合する

- 状態: 採用 (2026-08)
- 問題: ソース文字列を単純に連結すると、閉じていないフェンス、HTML ブロック、リスト、Setext 見出し、参照定義がファイル境界を越えて構文を変える
- 選択肢: (a) 区切りを挟んで文字列を連結してから 1 回構文解析する、(b) 各ファイルを独立して構文解析し、AST のブロック配列を結合する
- 採用: (b)。ファイル単体の構文とディレクトリー入力の構文が一致し、境界条件を局所化できる
- 非採用理由: (a) はどの区切りを選んでも、閉じていない全種類のブロックを安全に閉じられず、ソースファイルの末尾次第で次章の意味が変わる
- リスク: 参照定義などのパーサーの状態がファイル間で共有されない。これを仕様として明記し、共通リンクは通常のインラインリンクを使う
- 検証: フェンス、HTML、リスト、Setext 見出し、参照定義に関するファイル境界のフィクスチャー
- 再検討条件: ファイル間でパーサーの状態を共有する明確な利用要求が生じ、曖昧さのない境界構文を追加する場合

## DD-13: カスタムテンプレートは DOM スロットで組み立てる

- 状態: 採用 (2026-08)
- 問題: メタデータ、本文、目次、ロゴをカスタム HTML へ安全かつ曖昧なく挿入するための契約が必要
- 選択肢: (a) `{{...}}` の文字列置換、(b) 汎用テンプレートエンジン、(c) `data-pfpdf-slot` を持つ不活性な DOM を構文解析してノードを挿入する
- 採用: (c)。テキスト / ノードを挿入する文脈を固定でき、メタデータが属性や CSS へ意図せず入る経路を作らずに済む
- 非採用理由: (a) は文脈ごとのエスケープをテンプレート作者に委ね、プレースホルダーの重複・欠落も見逃しやすい。(b) は任意式、ヘルパー、バージョン管理という不要な API と依存を増やす
- リスク: 複雑な独自レイアウトの自由度は汎用エンジンより低い。生の HTML / スクリプト / CSS と省略可能なスロットで補い、互換性が必要な利用者には pfpdf のバージョン固定を求める
- 検証: 必須・重複・未知のスロット、メタデータのエスケープ、ロゴ / 目次の省略、スクリプトの準備完了待ちを確かめる単体・結合テスト
- 再検討条件: DOM スロットでは表現できない複数の実用テンプレートが確認された場合

## DD-14: 待機時間の上限と、検証後のアトミックな出力確定を必須にする

- 状態: 採用 (2026-08)
- 問題: スクリプト / ブラウザーが動作を停止して待機が続くことと、ヘッダーだけを持つ途中で切れた PDF が既存出力を破壊することを防ぐ
- 選択肢: (a) 上流プロセスを無期限に待ち、`%PDF-` だけ検査する、(b) 絶対時刻の期限、構造を認識した PDF の構文解析、フラッシュ、同一ディレクトリー内でのアトミックな置換を組み合わせる
- 採用: (b)。CI の永久停止を防ぎ、ヘッダー / EOF だけを持つ壊れた PDF を除外し、失敗時に既存出力を維持できる。期限は既定 300 秒で、1 秒から 1 時間の範囲で変更できる。上流にページネーション前のフックがない場合は、読込みを待機させるゲートとループバック経由の完了通知を使う。固定版レンダラーでこの方法を実証できることをリリース条件とする
- 非採用理由: (a) は信頼済みの入力でも無限ループ、ブラウザーのバグ、途中で切れた書込みに弱く、エラー時に直ちに停止する契約を満たさない
- リスク: 非常に大きい正当な文書では PDF の構文解析にかかる時間 / メモリーも増え、既定のタイムアウトを超える。明示的な上書きと、処理段階 / 経過時間の診断を提供する。構造の解析でもテキスト内容や見た目の意味までは保証できないため、CI では独立した `pdfinfo` / `pdftotext` / `pdffonts` を併用する

- 問題: 和文と欧文・数字が空きなしで隣接し、印刷物として読み取りづらい (#24)
- 選択肢: (a) 実際の空白をソース / DOM へ挿入する、(b) 新しいフロントマター / CLI 設定を導入する、(c) 既存の lang に基づき、CSS の text-autospace を日本語の既定値にする
- 採用: (c)。全同梱テンプレートの共通 CSS で、明示した lang が日本語の要素へ text-autospace: normal（ideograph-alpha / ideograph-numeric 相当）を適用し、別言語の部分木では解除する。code、pre、kbd、samp、textarea、SVG、MathML、数式とその子孫は対象外とする。セレクターの詳細度はゼロにし、利用者の CSS で上書きできる
- 非採用理由: (a) は URL・識別子・コピー文字列を変更する。(b) は既存の文書言語で決まる組版のために設定を増やす。約物の自動調整や置換は今回の範囲へ含めない
- 実装互換性: 固定版 Chrome 150 は normal を受け付けるが、ideograph-alpha ideograph-numeric の組合せ値を受け付けない。そのため、[CSS Text 4](https://drafts.csswg.org/css-text-4/#text-autospace-property) で同じ動作と定義される normal を使う
- 非対応時の動作: 非対応ブラウザーは CSS プロパティを無視し、従来の空きなしで変換する。依存やレンダラーの更新は行わない
- 検証: 固定版 Chrome 150 / Vivliostyle 11.1.0、全 7 テンプレートのゴシック・明朝、ラテン文字 / 数字、明示空白、約物、リンク、入れ子の lang、コード / 数式、DOM テキストと選択結果の保持、レンダラーが実際に使う document.html の計算済みスタイル / 要素の位置・寸法と PDF の文字位置・抽出結果
- リスク: 自動空きで改行位置が変わる。PDF 抽出器が視覚的な空きを空白として復元する可能性はあるが、DOM の元テキストは変更しない
- 再検討条件: ブラウザー間で既定の空き量や対応範囲が変わる場合、または CSS の上書きより文書設定での切替が必要になった場合

## DD-56: 悪意ある変更も想定してレビューし、メンテナーが最小限の修正を引き受ける

- 状態: 採用 (2026-10-31)
- 問題: PR の背景を知らない第三者にも、変更の目的、影響、検証の限界、残る課題が分かるレビューが必要である。投稿者への信頼やテストの成功だけでは、不正なコードや意図しない挙動の混入を防げない
- 選択肢: (a) 指摘を列挙して投稿者に修正を任せる、(b) メンテナーが広範に書き直して取り込む、(c) 悪意ある変更を想定して全差分を調査し、メンテナーが目的に必要な修正を用意して最終差分を検証する
- 採用: (c)。調査から再レビューまでの手順を `docs/reviewing.ja.md` にまとめ、AGENTS.md と CONTRIBUTING.md から参照する。コメントは「概要、影響範囲、確認した項目、現在の課題、今後の課題」の順とし、英語の後に同じ内容の日本語を書く。信頼している `main` の手順で変更を調べ、隔離環境で検証する。対象 SHA と未検証事項も記録する
- 修正方針: 原則としてメンテナーが修正する。元の PR の head から修正後までの差分と、最新の `main` へ入る最終差分を確認する。説明できない変更は除去するか、必要な部分を実装し直す。既存の実装を使って無関係な変更を避け、必要な回帰テストと日英の仕様更新は残す。メンテナー自身の変更にも同じ検査を適用する
- 非採用理由: (a) は、修正から検証までをメンテナーが進める方針に合わない。(b) は目的外の変更を増やし、全差分の確認を難しくする。修正コミットの行数だけを減らす案は、元の PR にある不要な変更を見落とし得るため採用しない
- リスク: 全差分の調査と隔離環境の用意には工数がかかり、検査しても不正な変更の不在を保証できない。確認済みと未確認を分けて記録し、重要な検証不足はマージ前に解消する。pfpdf は入力文書を信頼する方針を維持し、worktree や AssetServer を隔離の手段として扱わない
- 検証: 日英の手順、5 節の雛形、参照リンクの対応と、AGENTS.md の英語限定規則を確認する。`npm ci`、`npm test`、`npm run lint` を実行し、新しいチェックアウトで `make docs` により日英 4 冊を生成する
- 再検討条件: レビュー規模や実行環境が変わり、手順の自動化や役割分担を更新する必要が生じた場合

## DD-57: glob と minimatch の修正版を利用箇所に限定して固定する

- 状態: 採用 (2026-11-03)
- 問題: 配布する依存ツリーが、glob のキャンセル後の走査継続（[GHSA-3g3m-2fjr-6pw4](https://github.com/isaacs/node-glob/security/advisories/GHSA-3g3m-2fjr-6pw4)）と minimatch のパターン前処理の増幅（[GHSA-g3hv-75wg-m249](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249)）の対象版を含む。修正版はそれぞれ 14.0.2 と 11.0.1 で、既存の依存範囲を超える
- 選択肢: (a) 全ての親パッケージを最新版にする、(b) 全メジャーバージョンに一律の override をかける、(c) 親の使用 API を確認し、利用する親に限定した override と、旧 API を使う親の更新を組み合わせる
- 採用: (c)。Vivliostyle CLI 11.1.0 が使用する個々の親をルートの override のセレクターとし、glob を 14.0.3、minimatch を 11.0.2 に固定する。CLI 配下で何段も入れ子にした override は、npm 10 が一部の枝に適用しないため、各親を直接指定する。Arborist / map-workspaces / package-json / cacache は glob の Promise API、archiver-utils は `glob.sync` を使い、14 でも利用できる。minimatch の直接利用箇所である Arborist / map-workspaces / TUF models は `minimatch` / `match`、ignore-walk は `Minimatch.match` / `globParts` / `negate`、readdir-glob は `Minimatch.match` を使う。削除された `makeRe` / `matchOne` や RegExp の `set` 要素には依存しない
- 同梱マッチャー: glob 14.0.2 の既定の圧縮済みエクスポートは、未修正の minimatch 前処理コードを内包しており、別途インストールする minimatch の override では置き換わらないため採用しない。`**/../a/b` を 8 回繰り返し、`braceExpandMax: 32` を指定すると、既定の `Glob` コンストラクターは 256 パターンを生成する一方、`glob/raw` はインストール済みの修正版を使用して 32 パターンになる。再ビルド済みの glob 14.0.3 と、それが要求する minimatch 11.0.2 を使用し、実際の親経由で既定のエクスポートをテストする
- 旧 API: press-ready 配下の ShellJS とその型を上流の 0.10.0 に固定し、glob 7 / minimatch 3 の枝を除去する。ShellJS は fast-glob に移行しており、press-ready が使用する `which` を維持する。glob 7 を直接 14 に差し替えて、旧関数のエクスポート / コールバック契約を壊す案は採用しない
- 非採用理由: (a) の最新版 Arborist / map-workspaces は Node.js 22.22.2 以降を要求し、pfpdf の 22.12.0 互換性を失ううえ、依然として旧 minimatch を要求する。(b) は旧 API を壊し、無関係な依存にも影響する。Vivliostyle CLI、Markdown パーサー、CJK 拡張は更新しない
- 配布: DD-17 に従い `package-lock.json` と `npm-shrinkwrap.json` を同一内容にする。追加されるマッチャー / path-scurry / fast-glob 系を含め、最低 Node.js 要件は引き上げない。上流の glob 14 / minimatch 11 は、一部のパターン、Windows UNC、末尾スラッシュの一致規則を変更するため、監査の成功だけで互換性を判断しない
- 検証: 実際の親から解決した依存で、キャンセル後のディレクトリー読取り停止、制限付き前処理、Windows パス、ワークスペースの除外、ignore による再包含、アーカイブの glob / ZIP、キャッシュの検証・削除、ShellJS の実行ファイル探索を回帰検査する。通常の単体テスト / lint、日英 4 冊、PDF スモークテスト、配布 tarball の依存再現を検証し、他 OS の結果は CI と区別して記録する
- 配布検証の注意: npm 10.9.0 / 11.17.0 でローカルの `.tgz` を直接インストールすると、shrinkwrap を無視する既知の上流制限がある。レジストリーと同じ `_hasShrinkwrap` メタデータを使うローカルレジストリーでは、固定した依存ツリーが再現する。公開・デプロイは行わずにこれを検証する。既存のリリース手順どおり、展開したパッケージのルートでの `npm ci --omit=dev` / `npm ls` / ロック比較 / PDF スモークテストも行う。利用者のプロジェクトからの `npm ls` は、親の依存範囲を超える override を invalid と表示し得るため、正確な版と完全性の検査と区別する
- 再検討条件: 親が修正版を正式に採用したら override を除去する。新しいアドバイザリーまたはパターン互換性の問題が判明したら再評価する
