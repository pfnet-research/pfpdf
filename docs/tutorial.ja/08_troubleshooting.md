# 8. トラブルシューティング

## 8.1 まず `--doctor`

問題が起きたら、最初に `--doctor` を実行してください。

```bash
npx @pfnet-research/pfpdf@latest --doctor
```

Node.js のバージョン、ブラウザーの有無、フォント、出力先の権限などを検査し、問題を対処方法とともに報告します。`--input` / `--output` を付けて実行すると、その文書のリソースと書き込み先も検査します。結果は、バージョン付きスキーマの JSON オブジェクト 1 個として標準出力（stdout）へ出すため、CI でも解析できます。通常のログは標準エラー出力（stderr）へ出します。

`checks` の各項目の `status` は、`pass`（成功）、`warning`（警告）、`fail`（失敗）、`not-run`（未実行）のいずれかです。対処後は同じ引数で `--doctor` を再実行し、失敗した検査が `pass` になったか確認してください。文書を再変換したら、終了コードが `0` で、出力 PDF が期待した内容になっていることを確認します。

`--doctor` はブラウザーのダウンロード、プロジェクトや出力ディレクトリーの作成、OS の設定変更を行いません。ブラウザーを実際に起動する検査には専用の一時プロファイルを使い、検査後に削除します。

設計では、外部プロセスの各検査を後始末も含めて 10 秒、コマンド全体を 60 秒で打ち切ることを求めています。現在の実装では、ブラウザー検査の描画期限を 10 秒に設定し、検査用の子プロセスが 12 秒を超えたら終了を要求します。コマンド全体の期限はまだ実装されていません。

ブラウザーの検査に失敗した場合は、`checks` で `id: "browser"` の項目にある `message` を確認してください。終了コード・シグナル・タイムアウトの情報と、子プロセスの標準エラー出力が含まれます。標準エラー出力の抜粋は UTF-8 で最大 4 KiB とし、長い場合は先頭と末尾を残して省略を明示します。未知のエラーでも、この抜粋から詳細を確認できます。

root 実行、ユーザー名前空間や AppArmor の制限、その他のサンドボックス起動失敗、共有ライブラリーの不足、実行ファイルの問題といった既知の失敗には、原因の目安も付けます。診断は JSON の文字列として出力するため、標準エラー出力内の改行が標準出力の JSON を分割することはありません。

設定が意図どおりに効いているか確認したいときは `--print-effective-config` を使います。各設定値と、その設定元が CLI・フロントマター・既定値のどれかを JSON で表示します。フロントマターの `template` / `toc` / `cover` / `logo` を確認する場合は `--input` も指定します。

## 8.2 Node.js のバージョンが古い

pfpdf は起動直後に Node.js のバージョンを検査し、対応範囲外ならエラーを表示して終了します（終了コード `1`）。README に記載された semver の範囲内の Node.js を導入してください。単にバージョンの数値が新しければ常に対応するとは限りません。

## 8.3 ブラウザーのダウンロードが失敗する

初回実行時の Chromium は、同梱の Vivliostyle CLI とそのブラウザーマネージャーの標準機構で取得します。

- プロキシーやカスタム CA が必要な環境では、Vivliostyle CLI / Puppeteer の手順に従って設定してください
- 既に互換性のあるブラウザーがある場合は、`--browser-path` で明示できます

## 8.4 Linux でブラウザーが起動しない（共有ライブラリーの不足）

Linux では、ブラウザー本体に加えて OS の共有ライブラリーが必要です。`--doctor` で不足しているライブラリーを確認し、使っているブラウザーのリビジョンに必要なパッケージを調べてください。パッケージ名はディストリビューションとリリースによって変わるため、別のリリース向けの名前をそのまま使ってインストールしないでください。実行環境の前提は、設計書第7章「互換性とテスト」に記載しています。

pfpdf が root 権限でパッケージを自動インストールすることはありません。OS のパッケージを追加する場合は、利用しているディストリビューションのパッケージマネージャーと運用方針に従い、明示的にインストールしてください。

## 8.5 Linux でサンドボックスが起動できない

共有ライブラリーが揃っていても、Ubuntu 23.10 以降の非特権ユーザー名前空間の制限などにより、Chromium のサンドボックスを起動できない環境があります。これはライブラリー不足とは別の問題で、pfpdf の診断でも区別して報告されます。

- `root execution refused` は、ブラウザーが root 実行を拒否したことを示します。非 root ユーザーで実行してください
- `user namespace or AppArmor restriction` は、非 root でも起きるホスト側の制限を示します
- `browser sandbox unavailable` は、その他のサンドボックス起動失敗の目安です

いずれも `message` 内に残した元の標準エラー出力と合わせて確認してください。ホスト側の制限を回避するには、root 権限での設定変更が必要です。例えば Ubuntu では、Chromium の実行ファイルに対する AppArmor プロファイルを追加する方法があります。変更できない環境では、サンドボックスを利用できる別の対応環境で変換してください。

### Docker で実行する（Ubuntu 24.04、amd64）

リポジトリー内の `examples/docker/ubuntu24.Dockerfile` は、Ubuntu 24.04 上で Node.js 22.23.2 とロックファイルに固定した依存関係を使い、pfpdf をビルドします。ブラウザーの共有ライブラリーと、初回ダウンロードの展開に必要な `unzip` を含み、実行ユーザーは非 root です。対象アーキテクチャーは amd64 です。Arm64 ホストでは Docker の amd64 エミュレーションが必要です。

リポジトリーのルートで次を実行します。ホスト側でも非 root ユーザーを使い、出力先とキャッシュには、そのユーザーが所有するディレクトリーを使ってください。

```bash
docker build --platform linux/amd64 \
  -f examples/docker/ubuntu24.Dockerfile -t pfpdf-ubuntu24 .
PFPDF_CACHE_DIR="${XDG_CACHE_HOME:-$HOME/.cache}/pfpdf-docker"
mkdir -p input output "$PFPDF_CACHE_DIR"
cat > input/memo.md <<'EOF'
---
title: Docker example
lang: en
---
# Memo

PDF from a container.
EOF
docker run --rm --platform linux/amd64 --init \
  --cap-add=SYS_ADMIN --user "$(id -u):$(id -g)" \
  --env SOURCE_DATE_EPOCH=0 \
  --mount "type=bind,source=$(pwd)/input,target=/input,readonly" \
  --mount "type=bind,source=$(pwd)/output,target=/output" \
  --mount "type=bind,source=$PFPDF_CACHE_DIR,target=/cache" \
  pfpdf-ubuntu24 --input /input/memo.md --output /output/memo.pdf
```

`SYS_ADMIN` は、このコンテナーで Chromium のサンドボックスを起動するためのケーパビリティーです。[Puppeteer の Docker 手順](https://pptr.dev/guides/docker)でも、サンドボックスを使うためにこのケーパビリティーを要求します。ケーパビリティーの追加を許可している運用環境で使ってください。pfpdf は信頼済みの文書を処理することを前提とし、root での変換やサンドボックスを無効にする CLI オプションは提供しません。

入力は読み取り専用、出力と `/cache` は書き込み可能としてマウントします。`--user` でホストと同じ UID / GID を使うため、出力の所有者もホストのユーザーになります。`HOME=/tmp`、`XDG_CACHE_HOME=/cache` はイメージに設定済みです。

初回は Chromium を `/cache/vivliostyle/browsers` へダウンロードし、同じキャッシュディレクトリーをマウントした 2 回目以降は再利用します。変換後に、`docker run` の末尾にある `--input /input/memo.md --output /output/memo.pdf` を `--doctor` に置き換えて実行すると、ダウンロード済みブラウザーの起動を検査できます。空のキャッシュで `--doctor` を実行した場合は、ダウンロードせずに `warning` を返します。

`root execution refused` が出た場合は、実行 UID を確認してください。非 root で `user namespace or AppArmor restriction` / `No usable sandbox` が出る場合は、ケーパビリティー、Docker の seccomp ポリシー、ホストのユーザー名前空間や AppArmor のポリシーを確認します。Ubuntu 24.04 ホストの制限は、コンテナー内のユーザーを変更するだけでは解除されません。[Ubuntu の AppArmor の説明](https://ubuntu.com/server/docs/how-to/security/apparmor/)を参照し、ホスト管理者にブラウザーに適したプロファイルを用意してもらうか、サンドボックスを利用できるホストで実行してください。ホスト全体の保護を無効にする手順は、既定の実行例には含めません。

検証した環境は、Ubuntu 24.04 amd64 コンテナー、Node.js 22.23.2、Vivliostyle CLI 11.1.0、管理対象の Chrome 150.0.7871.115 です。Arm64 の Docker デーモンで amd64 をエミュレーションし、新規キャッシュ・再利用キャッシュ、読み取り専用の入力、ホストのユーザーが所有する出力、`--doctor` の成功を確認しました。root 実行の拒否と、ケーパビリティーがない場合の起動失敗も確認しました。Ubuntu ホスト固有の AppArmor プロファイルの実機検証は、別途必要です。

## 8.6 日本語が豆腐（□）になる / フォントが意図と違う

- 同梱テンプレートでは既定で同梱の日本語フォントを使うため、通常は豆腐になりません
- カスタムテンプレートで独自のフォントファミリーを指定している場合は、そのフォントが利用可能か、`font-family` の候補に同梱フォントを含めているか確認してください
- OS にインストールされたフォントを使いたい場合は、`--host-fonts` / `--font-dir` を明示してください（第6章参照）。フォントに関する警告や詳細な診断は、`--log-level debug` と `--doctor` で確認できます

## 8.7 数式やコードハイライトが効かない

- 数式・コードハイライトは同梱アセットで動作し、ネットワークは不要です
- `$` を数式にしたくない場合は `\$` とエスケープしてください（第5章参照）
- 文書内の `<script>` で描画開始の準備が完了する前にエラーが起きると、変換全体が失敗します。非同期描画は `window.pfpdf.registerReady(promise)` へ登録してください。`--keep-work-dir` で `document.html` とレンダラーの診断情報を残して確認できます

## 8.8 描画がタイムアウトする

- 既定の期限は、ブラウザーの準備、描画開始の準備が完了するまでの待機、描画、PDF の後処理・構造検査を合わせて 5 分です。`--log-level debug` のログで、どの処理に時間がかかったか確認してください
- リモートリソース、登録したまま完了しない Promise、スクリプトの無限ループ、巨大な画像、過度に複雑な CSS がないか確認してください
- 正常な文書でもサイズが大きくて期限を超える場合は、`--render-timeout-ms` を増やせます。`0` で無期限にはできません
- タイムアウト後に既存 PDF は上書きされません。子プロセスを強制終了するまで短い猶予があるため、CLI の終了を待ってから再実行してください

## 8.9 出力ファイルが更新されない

変換に失敗した場合、既存の出力 PDF は上書きされずにそのまま残ります。終了コードを確認してください（`0` 以外は失敗です）。CI では `pfpdf` の終了コードをそのまま判定に使えます。

PDF のヘッダーや最後の `%%EOF` がない不完全な出力に加え、相互参照表（xref）・カタログ・ページツリーが壊れた出力、暗号化された出力、0 ページの出力も失敗として破棄されます。

Windows では、ビューアーが既存 PDF を排他的に開いていると、最後のファイル置換に失敗する場合があります。その場合はビューアーを閉じて再実行してください。pfpdf は、置換のために既存 PDF を先に削除しません。

`SIGKILL` や電源断の直後には、出力ディレクトリーに `.pfpdf-...tmp` が残る場合があります。別のプロセスのファイルを誤って消さないよう、pfpdf はこれらを自動的に削除しません。pfpdf のプロセスが動いていないことを確認してから、手動で削除してください。

## 8.10 それでも解決しないとき

- `--log-level debug` で詳細なログとスタックトレースを確認してください
- `--keep-work-dir` でビルド用の作業ディレクトリーを残し、生成された `document.html`、リソースマニフェスト、レンダラーの診断情報を確認してください
- 問題を報告する際は、OS とアーキテクチャー、Node.js と pfpdf の各バージョン、`--doctor` の出力を添えてください

画像のエラーでは、元のファイル名・行番号・参照先を確認してください。Markdown の `![caption]()` は、入力の準備時に参照先が空であるため失敗します。

生の HTML の `img` は、`window.pfpdf.registerReady(promise)` に登録した Promise の完了後に検査します。スクリプトで `src` を設定する場合は、その非同期処理を登録してください。画像の破損、HTTP エラー、通信の失敗では、元の参照先と解決後の URL が診断に含まれます。画像の診断では HTTP ステータスまでは分からないため、必要に応じて参照先のサーバーログも確認してください。失敗時は既存 PDF を保持します。
